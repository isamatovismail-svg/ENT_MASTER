# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

The development roadmap is in `PLAN.md` (stages 1–6, in Russian). When asked to do «этап N», follow that section and the constraints at its top.

ENT MASTER — a website for preparing for the ЕНТ (Kazakhstan's Unified National Test): full mock exams, per-subject practice, answer review, attempt history. UI text, comments, docstrings and the README are in Russian; keep new code consistent with that.

**Hard constraint:** Python 3.11+ standard library, HTML and CSS only. No JavaScript (the CSP header forbids all scripts), no frameworks, no third-party packages / `pip install`.

## Commands

```bash
python seed.py      # validate data/questions/*.json and upsert into SQLite (idempotent, keyed on subject+text)
python manage_admin.py <login> [--revoke]   # grant/revoke the admin role (user must be registered)
python bot.py       # Telegram bot (long polling); needs TELEGRAM_BOT_TOKEN in .env (see .env.example)
python main.py      # init DB and serve on http://localhost:8000 (127.0.0.1:8000 from config.py)
python backup.py    # gzip backup of the SQLite DB into BACKUP_DIR, keeps BACKUP_KEEP copies (--telegram: also send it)
python notify.py test   # test Telegram alert to the main admin
python run.py       # site + bot together (two subprocesses, logs prefixed [САЙТ]/[БОТ], Ctrl+C stops both; bot skipped with a warning if no token)
python run.py --share   # + Cloudflare Quick Tunnel (cloudflared): prints a public https://….trycloudflare.com link, passes SHARE_MODE=1 and SITE_URL to site/bot

python -m unittest                                              # all tests
python -m unittest tests.test_auth                              # one module
python -m unittest tests.test_scoring.ScoreTests.test_matching  # one test
```

The local DB is `ent_master.sqlite3` in the repo root (gitignored). There is no linter/build config. The shared PyCharm run configuration «Run» (`.idea/runConfigurations/Run.xml`, the only tracked part of `.idea/`) launches `run.py`.

## Architecture

Request flow: `app/server.py` (`ThreadingHTTPServer` handler: parses request/cookies, serves `/static`, sets security headers, turns exceptions into a generic error page) → `auth.attach_user` resolves the session cookie → `router.dispatch` matches the `ROUTES` table (`<int:x>` / `<x>` path params; more specific paths must come first; path-match-but-wrong-method → 405) → view function in `app/views.py` → returns `web.Response`.

- **`config.py` is the single source of truth for exam structure**: subjects (`SubjectInfo` with per-question-type quotas), allowed profile pairs, points per question type, durations, security params. Totals (120 questions / 140 points) are derived from quotas — change the format here, not in logic code.
- **`app/database.py` holds all SQL** (parameterized only) and the dataclasses `User`, `Attempt`, `AttemptQuestion`. JSON columns (`options_json`, `correct_json`, `answer_json`, `subjects_json`, `shortage_json`) store lists. `database.configure(path)` swaps the DB file (used by tests). Schema changes to existing tables go in `_ADDED_COLUMNS` — `init_db()` ALTERs old databases, so the user's local `ent_master.sqlite3` survives upgrades.
- **Option shuffling**: each `attempt_questions` row stores `option_order_json` (shown index → original index). `get_attempt_questions()` returns options and `correct` already remapped to the *shown* letters, and `answer_json` is stored in shown letters — so all scoring/parsing/rendering code works in shown letters only. Explanations in `data/questions/*.json` must therefore never reference option letters.
- **`app/ent_logic.py`**: building attempts and scoring. `build_mock` picks random questions per subject per quota; if the bank is short it uses what exists and records a `shortage` list on the attempt, which the UI displays. Questions are shuffled within each subject. Scoring: single/context = 1 point; matching/multiple = 2 points with no mistakes, 1 with one mistake. Timer is server-side: `deadline` stored on the attempt (`mock_duration_minutes`: 240 × questions/120, ceil), expired attempts are auto-finished on the user's next request (`finish_expired_attempts`).
- **Two test modes with different UIs**: mock exam (`/attempt/<id>/<subject>`, no answer highlighting until the result page) and practice (`/practice/<id>`, one question per page: POST checks it via `check_practice_answer` → sets `checked=1`, then `/practice/<id>/review/<n>` shows red/green + explanation). Section/finish-confirm views redirect practice attempts to `/practice/<id>`; both modes finish via `POST /attempt/<id>/finish`.
- **CSP forbids inline `style` attributes** (and all scripts). Dynamic visuals use classes instead: `.subj-<code>` sets per-subject `--c1/--c2` colors (defined in `static/style.css`, emoji icon in `config.SubjectInfo.icon`), `.p-0…p-100` (step 5) for the result ring, and `<progress>` for bars. Dark theme is `prefers-color-scheme` overriding CSS variables.
- **Admin panel** (`app/admin_views.py`, routes under `/admin`): every view is wrapped in `admin_required` (= `views.login_required` + `user.is_admin`, else 403). `users.role` is `'user'`/`'admin'`. Question deletion is soft (`questions.deleted = 1`) when the question appears in any attempt, hard otherwise; every bank query (`random_questions`, `question_counts`, `list_questions`, `get_question`, admin `update_question`/`delete_question`) must filter `deleted = 0 AND status = 'approved'`, while `get_attempt_questions` must not (old reviews keep working). Question validation lives in `app/question_bank.py`, shared by `seed.py` and the question form (`app/question_form.py`: `QuestionForm`, `form_from_request`, `build_question`, `form_content`, `preview` — used by both the admin panel and teachers; template `question_form.html`). Admin edits go to the DB only. `seed.py` overwrites/undeletes questions whose text matches the JSON/generated ones, except questions created or edited in the admin panel (`questions.edited_by_admin = 1`, set by `insert_question`/`update_question`; the upsert has `WHERE edited_by_admin = 0`). `views.result_content()` renders a result for both the student page and the admin attempt view.
- **Telegram bot** (`app/telegram_bot.py`, `bot.py`): stdlib `TelegramAPI` (urllib POST JSON) + `Bot.handle_update` + `run_polling`. The bot is stateless — multi-step answer state (checked letters for multiple, per-row letters for matching) lives in `callback_data` (`a:`/`t:`/`m:<attempt>:<aq>:<letters>`, ≤64 bytes). Bot practice uses the same `practice` attempts and `ent_logic.check_practice_answer` as the site, and requires a linked account (`users.telegram_id`, unique partial index created in `init_db`). Tests use a `FakeAPI` — never hit the network. `config.py` loads `.env` (`load_env`; real env vars win) for `TELEGRAM_BOT_TOKEN` and `SITE_URL`.
- **Telegram login** (`app/telegram_views.py`, `/tg/login`): one-time 10-minute tokens (`telegram_login_tokens`, SHA-256 stored). GET must never consume the token (link previews); consumption happens only on POST via `use_telegram_token`. Telegram-only accounts get login `tg<telegram_id>` and an unknown random password.
- **Email registration & Google login** (`app/account_views.py`, `app/mailer.py`, `app/google_auth.py`): `auth.register_user(first, last, email, phone, pw, pw2)` creates an account with `users.email_verified = 0` (old/Telegram/Google accounts are 1; the column default is 1 so migrated DBs count as verified); a re-registration on an unverified email overwrites it. Codes live in `email_codes` (one per user+purpose `verify`/`reset`, SHA-256 only, 15 min, 5 attempts, resend ≥60 s) via `auth.send_email_code` / `check_email_code` / `verify_email` / `reset_password`. Unverified users can't log in (login redirects to `/verify`) or link Telegram. `users.phone` is optional, unconfirmed, unique, and usable as a login (`get_user_credentials` matches `login` or `phone`). Mail goes through `mailer.send` (SMTP_SSL if `SMTP_*` set in `.env`, else printed to console); tests install `FakeMailer` in `DatabaseTestCase.setUp` (`self.mail.last_code(email)`). Google: `/auth/google` sets a `state` cookie and redirects; the callback checks it, calls `google_auth.exchange_code` (urllib POST, id_token `aud`/`iss`/`exp`/`email_verified` checked, signature not) and `auth.google_user` (login by email, create otherwise; an unverified pre-registration gets a random password). Tests patch `google_auth.post_form` and `config.GOOGLE_*`. Use `auth.create_account(name, login, password)` in tests for a ready verified user.
- **Schools & teacher cabinet** (`app/schools.py`, `app/teacher_views.py`, `/profile` in `views.py`): roles `user`/`teacher`/`admin` (`database.ROLE_*`, `User.is_teacher`). `users.school_id` + `school_status` (`pending`/`approved`/`rejected`) hold a student's school request; for a teacher it's the school they manage (set by `manage_admin.py <login> --teacher <city> <school>` → `database.make_teacher`; `--revoke` → `revoke_role`). Schools are deduplicated by `schools.key` = `school_key(city, name)` (casefold, drops «№», quotes, words like «школа»/«СОШ»). Every `/teacher/<int:school_id>/…` view is wrapped in `teacher_views.school_access` (teacher of that school or admin, else 403) and must look up students via `get_school_student` / members via `set_member_status(school_id, …)` and assignments via `get_assignment(id, school_id)` — never by id alone. Results are only visible for `approved` students. Assignments (`assignments` + `assignment_students`; `target` = subject code for practice, `"a,b"` or `""` for mock; `for_all` = dynamic «all approved students») count only attempts with `created_at < finished_at <= deadline` (`schools.assignment_progress`). `users.last_login_at` is set in `database.create_session`.
- **Teacher cabinet, notifications (stage 8)**: teachers get their own nav (Ученики / Задания / Мои вопросы / 🔔 / Профиль); `views.student_area` (dashboard, mock, practice, history) redirects teachers to `/teacher`. `/teacher/<id>` = requests + students table from `app/student_stats.py` (`school_overview(school_id, period)`, `PERIODS`, `SORT_KEYS`, help score, `timeline(user_id)` for the student card); `/teacher/<id>/assignments` lists assignments. Students start an assignment with `POST /assignments/<id>/start` (exact pair/subject). `app/notifications.py`: table `notifications` (kind + `params_json`, text rendered on display, `dedup_key` unique per user), events `school_request` (from `schools.join_school`), `request_decided`, `assignment_created` (from `schools.create_assignment`), `attempt_finished` (from `ent_logic.finish_attempt`), `check_due` (dashboard, `/notifications`, bot loop via `check_due_throttled`). Telegram copies go through `notifications.set_sender` (tests: `FakeTelegram` in `DatabaseTestCase`, `self.telegram`); failures are only logged. `ads.banner_block(placement, user)` shows banners only to guests/students.
- **Two UI languages (stage 9)**: `app/i18n.py` — Russian source text is the key of `KK_DICT` (Kazakh value); request language lives in a contextvar set in `server._build_response` via `views.request_language` (`users.language`, guest cookie `ent_lang`, `Accept-Language`). Python strings go through `t("… {n}", n=…)`; `render()`/`fragment()` translate the template's own text nodes and `placeholder/title/aria-label/alt` (values substituted after, never translated) — so never put UI text into `SafeHTML("…")`, use `fragment("…")`. Module-level labels use `i18n.Translated({...})` or `t(CONST)` at use; `SubjectInfo.name` / `Topic.name/section` are translating properties (`title`, `name_ru`, `section_ru` hold Russian). Use `i18n.use(lang)` for mail/Telegram to another person. Language switch: `GET /lang/<code>?next=`, profile `POST /profile/language`, registration field `language`. Every new UI string needs a `KK_DICT` entry — `tests/test_i18n.py` (with `app/i18n_keys.py`) fails otherwise and crawls kk pages for leftover Russian.
- **Questions in two languages (stage 10)**: `questions.language` (`ru`/`kk`, foreign language stored as `en`); bank queries take `language` (`database._language_filter`: subjects in `config.SHARED_LANGUAGE_SUBJECTS` and `config.SUBJECT_OWN_LANGUAGE` ignore it). `ent_logic.build_mock/build_practice` use `database.get_user_language(user_id)`; `config.pairs_for(lang)` hides the other language's «язык и литература» pair (`LANGUAGE_ONLY_PAIRS`). Kazakh JSON lives in `data/questions/kk/` (same order as the Russian file — `tests/test_kk_questions.py` diffs answers, numbers, formulas); Kazakh generators: `generators.templates_for(subject, "kk")` → `kk_gen.TEMPLATES` (`kk_computed.py`, `kk_facts.py`); `generators.generate(..., lang=)` sets `question["language"]`. `seed.language_table()` prints ru/kk counts.
- **Teacher questions & review**: `questions.status` = `pending`/`approved`/`rejected` (default `approved`, so JSON/generated/admin questions and migrated DBs are in the bank), `author_id` (teacher), `review_comment`, `submitted_at`, `reviewed_at`. Teachers use `/teacher/questions…` (`teacher_views.teacher_only`; queries always scoped by `author_id`: `insert_teacher_question`, `get_author_question`, `resubmit_author_question` and `delete_author_question` refuse approved questions). Admin reviews at `/admin/review` (`review_question`, `approve_with_changes` → sets `edited_by_admin`). The seed upsert skips rows with `author_id IS NOT NULL`.
- **Spec topics (stage 5)**: `app/topics.py` holds the NCT 2026 specification topics for every subject (`TOPICS[subject]` → `Topic(code "01".., section, name)`; NCT publishes no per-topic task shares). Every bank question has `questions.topic`: JSON `"topic"`, computed templates `@topic("NN")` (`generators.common.topic`), table templates take it from the row (`Event`/`Fact`/`Category.topic`, `facts.set_topics`, `facts.with_topic`), literature from `WORK_TOPICS` (works list = spec program only), fact quizzes via `common.quiz(items, code)`. `validate_question(q, subject)` checks the topic; the question form requires one. `seed.seed()` (full run, no errors) calls `database.retire_untagged_questions()` — soft-deletes untagged non-admin, non-teacher questions. `tests/test_topics.py::KNOWN_GAPS` lists the only topics allowed to have no questions (may only shrink). Weak topics: `ent_logic.topic_strengths` / `weak_topics` (< 60 %, ≥ 3 tasks); coverage report `/admin/topics`.
- **Deployment & ads (stage 6)**: production target is Oracle Cloud Always Free (Ubuntu 24.04) — `deploy/setup.sh` (root; iptables 80/443, user `ent`, `/opt/ent-master`, `.env`, systemd units `ent-master-site/bot/backup(.timer)`, Caddy → `127.0.0.1:8000` with automatic HTTPS) and `deploy/update.sh`. `config.py` reads `HOST`, `PORT`, `DATABASE_PATH`, `COOKIE_SECURE` (adds `Secure` to session/OAuth cookies), `BACKUP_DIR`, `BACKUP_KEEP` from `.env`. `backup.py` = `sqlite3` online backup + `integrity_check` + gzip + rotation. Uploads: `server.parse_multipart` (email.parser; `cgi` is gone in 3.13) fills `Request.form` and `Request.files` (`UploadedFile`); `MAX_REQUEST_BODY_BYTES` is 2 MB. Banners (`app/ads.py`, table `banners`, image stored as BLOB): admin CRUD at `/admin/banners`, image type checked by magic bytes (no SVG), shown via `ads.banner_block(placement)` on landing/dashboard/result/history only (never on test pages), served at `/ad/<id>/image`, clicks via `/ad/<id>` redirect. The paid part (≤ 500 тг) is intentionally not implemented yet (PLAN says decide later). Alerts (`app/alerts.py`, `notify.py`): Telegram messages to `config.ADMIN_TELEGRAM_CHAT_IDS` or linked admins (`database.admin_telegram_ids`), sent straight through `TelegramAPI` (works even if the bot process is down); site/bot units use `ExecStopPost=notify.py stopped %n` (silent when `SERVICE_RESULT=success`) and `OnFailure=ent-master-alert@%n.service`; `ent-master-health.timer` runs `notify.py healthcheck` every 5 min (alert after 2 failures, then recovery); repeats are throttled via `ALERT_STATE_PATH` (`ALERT_COOLDOWN_SECONDS`). The backup unit runs `backup.py --telegram` (`TelegramAPI.send_document`, multipart; exit 1 if not sent). Tests use `FakeSender` / a fake urlopen — never the network.
- **Local run & share mode (stage 7)**: the only printed link is `config.LOCAL_URL` (`http://localhost:8000`; Chrome may hold a cached 301 to https for `127.0.0.1:8000` from other projects). `server.RequestHandler.parse_request` drops TLS handshakes with a throttled hint instead of «Bad request version». `run.py` refuses to start on a busy port, children get `PR_SET_PDEATHSIG` and a double Ctrl+C can't skip `shutdown()`. In `SHARE_MODE` `auth.is_blocked_demo_admin` (admin role + `@entmaster.demo`) blocks login and ignores existing sessions; `auth.weak_admin_logins` is checked in the background. Redirects are relative, so the site works behind the tunnel unchanged.
- **Mock test UI without JS**: each subject section is one HTML form; the subject tabs and Back/Next/Save/Finish are submit buttons of that same form, so every navigation POSTs and saves the section's answers first (`section_submit`), then redirects.
- **`app/templates.py`**: `string.Template` files in `templates/` with `$name` placeholders. Every substituted value is `html.escape`d unless it is a `SafeHTML` instance. Build HTML fragments with `fragment()`/`join()`/`render()` so escaping is preserved — never wrap untrusted strings in `SafeHTML`. Missing placeholders raise `KeyError`. Views wrap content via `views.page()` into `base.html`.
- **Auth (`app/auth.py`)**: PBKDF2-SHA256 passwords; session cookie holds a random token, DB stores only its SHA-256. Phones in any form are normalized to `+7XXXXXXXXXX` by `auth.normalize_phone` (registration) / `normalize_login` (login, admin user search, `manage_admin.py`); `tg<id>` logins pass through unchanged. `views.login_required` redirects anonymous users to `/login?next=…` and enforces the CSRF token on all POSTs — new POST forms for logged-in users must include `_csrf_field(request)`. Queries for attempts must always filter by `user_id`.

## Question bank

`data/questions/<subject>.json` — one file per subject, `"subject"` must be a code from `config.SUBJECTS`. Every question requires a non-empty `explanation` (validated by `seed.py`). Types: `single`, `context` (adds `context`), `matching` (adds `left`; `correct` has one letter per `left` row, in order), `multiple`. Options are lettered A–H by position. `seed.py` validates and rejects malformed questions. See README.md for the full format.

## Question generators

`app/generators/` builds computed questions (math, math_literacy, physics, chemistry, informatics) from templates, and fact-based questions from tables (`facts.py`: `Event`/`Fact` tables → «в каком году», «год → событие», «кто», «чем известен», matching; plus `Category` tables for multiple-choice «выберите все…», context templates (`by_description` uses `note` without the name, `by_about`, event notes) and `build()` that assembles all four ЕНТ types for a profile subject; used by every non-computed subject (history, geography, biology, law, languages, literatures via `literature.py`); `lang="ru"|"kk"|"en"` picks the service phrases (`PHRASES`) — Kazakh subjects are written in Kazakh, foreign_language in English; a template that keeps raising `SkipQuestion` counts as exhausted, so it never loops forever; `what_phrases` keeps the «чем известен» wording valid for every option in a group). Only subjects in `NUMERIC_SUBJECTS` get thousands spacing (years must stay «1771»). Computed templates: each template is `fn(rng: random.Random) -> dict` returning a question in the JSON format, built via `common.single` / `multiple` / `matching` (they shuffle options and set `correct` letters; ЕНТ format: 4 options for single/context, 6 with 1–3 correct for multiple, 2 rows + 4 options for matching). Answers are computed in code, never typed. Every template must yield a question with a spec topic (see «Spec topics»); keep templates' skip rate low (pick numbers so the answer is «nice» instead of raising `SkipQuestion` most of the time). `generators.generate(subject, qtype, count, seed)` is deterministic and dedupes by `text` (the DB unique key is `(subject, text)`, so a template must put its varying numbers into `text`, not only into `context`/`left`); output passes `common.polish` (thousands spacing) and `validate_question`. Raise `SkipQuestion` for unlucky random values. `seed.py` loads JSON files and then generated questions via `database.upsert_questions` (one transaction); `--no-generated` skips them. `database.random_questions(..., user_id)` orders by how many times this user has already seen each question, then `RANDOM()`, so unseen questions come first (index `idx_attempt_questions_question`).

## Tests

`tests/base.py::DatabaseTestCase` gives each test a fresh temp DB and lowers `PBKDF2_ITERATIONS` for speed; `add_questions` / `fill_full_bank` create synthetic questions. `tests/test_pages.py` starts the real server in a thread on a free port with the JSON question bank seeded (`seed.seed(with_generated=False)`, its assertions depend on those counts) and drives it via a urllib-based `Browser` (cookies, CSRF extraction from forms).
